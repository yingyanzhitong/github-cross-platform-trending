先定需求和架构、再把边界明确的实现任务交给不同角色，最后必须回到独立审查，这条闭环正是 Sol Advisor 的组织方式。父聊天始终保留需求、架构、任务拆分、diff 检查、验证和验收的所有权，orchestrator 继承当前会话所选模型与推理强度；routine implementer 处理机械且规格完整的工作，high-complexity implementer 接手安全、并发、迁移或复杂调试，advisor 负责提交前审查和最终证据裁决。首次调用时会在父聊天启动 first-use interview，询问客户端、项目或用户作用域，以及从模型选择器复制的三个精确模型 ID；它不会猜测、归一化或静默回退。逻辑偏好保存在 ${PLUGINDATA}/config.json，而原生角色文件只有经过完整预览和与内容绑定的明确确认后才会生成。插件由 plugin.json、mcp.json、mcp/server.ts、setup 与 orchestration 两套 skill，以及兼容旧版 Codex 的 agents/ 和 scripts/ 构成；MCP 以 Bun 运行零第三方依赖的换行分隔 JSON-RPC 服务。Codex 可执行 codex plugin marketplace add DannyMac180/sol-advisor --ref main 后安装并在新聊天调用工作流。Cursor 3.15.6 因符号链接和 bare bun 解析存在宿主兼容问题，README 另给出受保护的本地安装器：它复制插件、只在指定项目的 .cursor/mcp.json 写入等价 MCP 配置，并通过收据、冲突拒绝和精确令牌保护安装与清理过程。
